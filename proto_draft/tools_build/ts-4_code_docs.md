# ts-4: מחולל תיעוד קוד ומפת קבצים

מודול: tools_build/ts-4 | פרויקט: protomotai | גרסה: 0.1 | סטטוס: טיוטה | מצב: דלוק | תלוי ב: tools_build | רמת סיכון: בינונית | עודכן: 2026-10-25 | עודכן על ידי: claude

- **סוג:** build (לייצור עצמי)
- **תחום:** תיעוד ואיכות קוד
- **למה נדרש:**
  - סוכן AI שפותח צ'אט חדש לא מכיר את הקוד. בלי מפה הוא קורא קבצים שלמים כדי למצוא דבר אחד, וזה עולה זמן וטוקנים ומגדיל את הסיכוי לטעות.
  - תיעוד שנכתב ביד מתיישן מהר: הקוד משתנה והמסמך נשאר מאחור.
  - בלי מדד, "התיעוד מלא" הוא תחושה ולא עובדה.

  הכלי מפיק את התיעוד החיצוני **מהקוד עצמו**, בודק שכל רכיב בקוד מתועד, וחוסם שמירה ב-git כשחסר תיעוד. כך התיעוד מתעדכן עם כל שינוי, בלי עבודה ידנית.

- **מה עושה:**
  - **קלט:** תיקיית הקוד של הפרויקט וקובץ הגדרות קטן (ראו "מה נדרש ליישום"). קוד המקור נקרא בלבד ולא משתנה.
  - **פלט:** תיקייה אחת של קבצי markdown (למשל `docs/generated/`). בראש כל קובץ הערה "נוצר אוטומטית, לא לערוך ידנית".
  - **מצב רגיל:** מפיק את כל המסמכים ומדפיס שורת סיכום: אחוז כיסוי ומספר הרכיבים החסרים.
  - **מצב `--check`:** אותו דבר, ובנוסף יוצא עם קוד כשל אם חסר תיעוד כלשהו. במצב הזה משתמשים השומר והסוכנים.

| קובץ פלט | תוכן |
|---|---|
| `README.md` | סדר קריאה מומלץ, ורשימת מודולים עם מספר המחלקות בכל אחד |
| `FILE_MAP.md` | כל קובץ: נתיב, מספר שורות, ותיאור בשורה אחת (מתוך תיעוד המחלקה, או מההערה הראשונה בקובץ) |
| `FUNCTION_INDEX/` | קובץ לכל מודול: שורה אחת לכל מחלקה, פונקציה, קבוע ומאפיין, עם מספר השורה בקובץ המקור |
| `REFERENCE/` | קובץ לכל מודול: טקסט התיעוד המלא, חתימות, טיפוסים וערכי ברירת מחדל |
| `DOC_COVERAGE.md` | כמה רכיבים נבדקו, כמה מתועדים, ורשימת החסרים בפורמט "רכיב - מה חסר" |
| תוספות לפי מתאם | נתיבי API, מבנה בסיס הנתונים, פקודות, שמות משתני סביבה (שמות בלבד), קטלוג בדיקות |

  **סדר קריאה לסוכן:** קודם `FILE_MAP.md`, אחר כך האינדקס של המודול הרלוונטי, ורק אם צריך את `REFERENCE/` או את קובץ המקור בשורה שצוינה. עוצרים ברגע שיודעים איפה הקוד.

- **איך הוא בנוי (ארבע שכבות):**
  1. **איסוף:** סורק את התיקיות שהוגדרו, ומכל קובץ קוד מחלץ מחלקות, פונקציות ומתודות, קבועים ומאפיינים, חתימות, מספרי שורות ואת בלוק התיעוד של כל רכיב. התוצאה היא מבנה נתונים אחיד אחד, ממוין לפי שם.
  2. **כללי תיעוד ובדיקת כיסוי:** על כל רכיב מופעלים כללי התיעוד (ראו למטה). כל בדיקה נספרת, וכל כשל נרשם כשורה "רכיב - מה חסר".
  3. **הפקה:** ממבנה הנתונים נכתבים קבצי ה-markdown. הפלט **דטרמיניסטי**: מיון קבוע, בלי חותמות זמן ובלי נתונים שמשתנים בין ריצות. כך השוואת גרסאות ב-git מראה רק שינויים אמיתיים בקוד.
  4. **שילוב בתהליך:**
     - **שומר pre-commit:** מריץ `--check`. אם חסר תיעוד, השמירה נחסמת. אם הבדיקה עוברת, המסמכים המעודכנים נכנסים לאותה שמירה.
     - **כלל לסוכנים:** אחרי כל איחוד קוד ולפני עלייה לאוויר מריצים `--check`. כישלון הוא ממצא, לא "נתקן אחר כך".
     - **אין עקיפה:** לא עוקפים את השומר (`--no-verify`). אם הוא חוסם בטעות, עוצרים ושואלים את הבעלים.

  **כללי התיעוד (ברירת מחדל, אפשר להחמיר):**
  - לכל מחלקה, פונקציה, מאפיין וקבוע יש שורת תקציר.
  - פרמטר או ערך חוזר בלי טיפוס מדויק (רשימה או מילון כלליים, או בלי טיפוס בכלל) מחייב תיאור של המבנה.
  - פונקציה שיורשת את התיעוד שלה מסומנת במפורש (למשל `inheritDoc`) ולא נספרת כחסרה.
  - כל בדיקה (test) כוללת שורת תיאור ותג תחום מתוך רשימת תחומים מוגדרת. כך קטלוג הבדיקות שימושי, ולא נוצרות בדיקות כפולות.

- **מה נדרש ליישום:**
  - **בחירת גישת איסוף.** זו ההחלטה החשובה ביותר:

| גישה | איך | יתרון | חיסרון | מתי משתמשים |
|---|---|---|---|---|
| ניתוח סטטי (מומלץ) | קריאת הקבצים כטקסט וניתוח תחבירי בלי להריץ קוד. ב-Python: המודול `ast` מהספרייה הסטנדרטית. בשפות אחרות: מנתח תחביר של השפה, או כלי כמו ctags | לא מריץ שום קוד; מתאים גם לפרויקט שאינו שלכם | פחות מדויק בירושה, בטיפוסים דינמיים ובקוד שנוצר בזמן ריצה | ברירת מחדל, ובכל פרויקט נסרק |
| Reflection מתוך האפליקציה | פקודה שרצה בתוך האפליקציה וקוראת את המחלקות הטעונות (למשל פקודת CLI של ה-framework) | מדויק מאוד; מאפשר גם נתיבי API, סכמת בסיס נתונים ופקודות | **טוען ומריץ את קוד הפרויקט** (קוד אתחול וקבצי הגדרות) | רק בפרויקט שלכם ובסביבה מבודדת (קונטיינר פיתוח); אף פעם לא על פרויקט נסרק |

  - **מבנה מוצע: ליבה ומתאמים.**
    - **ליבה** (לא תלויה בשפה): מעבר על קבצים, מפת קבצים, מבנה נתונים אחיד, מנוע כללים, הפקת markdown ומצב `--check`.
    - **מתאם לכל שפה:** מחלץ רכיבים ותיעוד לפורמט האחיד. המתאם הראשון המומלץ הוא Python (`ast`), כי אפשר לבנות ולבדוק אותו בלי תלויות חיצוניות.
    - **מתאמי framework (אופציונלי):** נתיבי API, סכמת בסיס נתונים ופקודות. הם ספציפיים ל-framework, ובדרך כלל דורשים את גישת ה-Reflection.
  - **קובץ הגדרות** במקום ערכים שכתובים בתוך הקוד: תיקיות לסריקה, תיקיות לדילוג (`vendor/`, `node_modules/`, תיקיות build), תיאור לכל מודול, תיקיית פלט, רשימת תחומי בדיקות, ואילו מתאמים פעילים.
  - **כתיבה בטוחה של הפלט:** כותבים קודם לתיקייה זמנית, ורק אחרי הצלחה מחליפים את תיקיית הפלט. לא מוחקים את הפלט הקיים לפני שהחדש מוכן, כדי שכשל באמצע לא ישאיר את הפרויקט בלי תיעוד.
  - **סביבה:** Python 3 לליבה ולמתאם Python, ו-git לשומר. בגישת Reflection: סביבת הריצה של האפליקציה, רצוי בקונטיינר.
  - **היקף משוער:** ליבה ומתאם Python: כ-300-400 שורות ועוד בדיקה עצמית. מתאם framework מלא (נתיבים, בסיס נתונים, פקודות, קטלוג בדיקות): כ-800 שורות.
  - **רישום:** אחרי שהכלי נבנה ואומת, רושמים אותו ב-`tools.md` של הפרויקט (`tool-<n>`). "מתי מפעילים": לפני כל commit (דרך השומר), אחרי איחוד קוד, ולפני עלייה לאוויר.

- **סיכון ואכיפה:**
  - הפקה ובדיקה (`--check`) בגישה הסטטית: R0 לגבי קוד המקור (קריאה בלבד). כתיבת תיקיית הפלט: R1.
  - גישת Reflection מריצה קוד של הפרויקט, ולכן היא R2 בהפעלה הראשונה בכל סביבה, ורק בפרויקט שלכם.
  - התקנת השומר בפרויקט: R1, באישור ממוספר. השומר עצמו: enforced. הכלל לסוכנים: instruction-only, וההליך המכני המשלים שלו הוא השומר.

- **כללי כשל-סגור:**
  - קובץ שאי אפשר לנתח (שגיאת תחביר, קידוד לא מוכר) נרשם כחסר ב-`DOC_COVERAGE.md`, ו-`--check` נכשל. לא מדלגים עליו בשקט.
  - אם נסרקו 0 קבצים (נתיב שגוי או הגדרות ריקות), זה כשל ולא "100% כיסוי".
  - תג תחום בדיקה שלא מופיע ברשימת התחומים נספר כחסר.
  - נתיב שמסומן deny או mask ב-`sensitive_paths.md` לא נקרא. במפת הקבצים מופיע לכל היותר שמו, עם הסימון "לא נסרק".
  - משתני סביבה: רק שמות, אף פעם לא ערכים. קובץ `.env` לא נקרא.
  - כישלון בכתיבת הפלט: יציאה עם קוד כשל, והפלט הקודם נשאר כמו שהוא.
  - הכלי לא מדפיס לצ'אט תוכן של קבצים, רק סיכום ונתיבים.

- **בדיקות קבלה:**
  1. פונקציה בלי תיעוד מופיעה ב-`DOC_COVERAGE.md`, ו-`--check` מחזיר כשל.
  2. אחרי הוספת תיעוד לאותה פונקציה, `--check` עובר.
  3. שתי ריצות רצופות בלי שינוי בקוד מפיקות פלט זהה בית-לבית.
  4. קובץ עם שגיאת תחביר נרשם כחסר, ו-`--check` נכשל.
  5. נתיב שגוי או 0 קבצים: כשל עם הודעה ברורה.
  6. קובץ ברשימת deny לא נקרא. בודקים עם קובץ דמה שמכיל ערך מזהה שאסור שיופיע בפלט.
  7. ערך של משתנה סביבה לא מופיע בפלט, רק השם שלו.
  8. כשל מדומה באמצע ההפקה משאיר את תיקיית הפלט הקודמת שלמה.
  9. השומר חוסם commit כשיש חסר, ומוסיף לשמירה את המסמכים המעודכנים כשאין.
  10. בגישה הסטטית לא מורצת אף שורת קוד של הפרויקט. בודקים עם קובץ דמה שיוצר קובץ סימון אם הוא מורץ.

- **מקור:** לא רלוונטי
- **pin:** לא רלוונטי
- **verify_command:** לא רלוונטי
- **פרוטוקול אבטחה:** אין בגישה הסטטית (כלי קריאה בלבד שאינו מוריד ואינו מריץ קוד חיצוני). אם משתמשים ב-ctags או במנתח חיצוני אחר: `security/downloads_installs.md`, והתקנה עם pin ו-verify_command דרך `tools_install/`.
- **הערות:**
  - נגזר מכלי שנבנה ונבדק בניסיון קודם: פקודת Reflection בתוך האפליקציה, עטיפת shell ושומר pre-commit שאכף כיסוי תיעוד מלא. הפרטים כאן הם תיאור כוונה לגרסה גנרית, ולא תיאור של קוד המקור.
  - שני שינויים מכוונים לעומת המקור: (א) ברירת המחדל היא ניתוח סטטי שלא מריץ קוד; (ב) כתיבה לתיקייה זמנית והחלפה, במקום מחיקה ובנייה מחדש.
  - לקח מהמקור: לא להעביר את פלט הכלי ל-`head` או ל-`grep -q`. סגירת הצינור באמצע עלולה לעצור את הכלי אחרי שמחק את הפלט הישן ולפני שכתב את החדש. בגרסה הגנרית הכתיבה לתיקייה זמנית פותרת את זה, אבל עדיף בכל מקרה להפנות את הפלט לקובץ.
  - קשור ל-`ts-1` (קטלוג בדיקות): תגי התחום בבדיקות מזינים את הקטלוג.
  - אפשרות עתידית, שעוד לא הוחלטה: מודול `code_docs` בפרוטוקול (כבוי כברירת מחדל) שיחייב את הכלל לסוכנים.
